## Caching Vector Search Results in RAG Pipelines

When I build Retrieval-Augmented Generation (RAG) systems, I often cache vector search results to reduce latency. The pattern is pretty straightforward: after the initial embedding-based query, I store the top-k document IDs and their embeddings in Redis (or a similar store). The tradeoff here is between cache freshness and speed. If the underlying document store changes frequently, cached results can become stale, leading to irrelevant context for the LLM.

For example, in one setup, I cached the top-5 hits for each unique user query (normalized/lowered), which cut the response time from ~1.1s to ~0.3s on repeat queries. The lesson: if your corpus updates daily or less, you can invalidate the cache on schedule (e.g., every night). But if users expect real-time updates, caching can backfire unless you track document versioning. I learned to always include a version hash in the cache key, so any document update triggers a cache miss. This simple trick prevented users from seeing outdated info without ditching the performance boost.
