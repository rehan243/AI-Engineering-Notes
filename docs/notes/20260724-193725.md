## Tradeoff: Batch Size vs. Latency in Online Inference

One tradeoff I've run into repeatedly is between batch size and latency for online inference. Larger batch sizes let you utilize GPU hardware more efficiently, especially for matrix-heavy operations like those in transformer models. But the downside is added latency because you have to wait for enough requests to accumulate before processing a batch.

For example, when I deployed a BERT-based model for real-time predictions, a batch size of 1 gave sub-30ms latency but kept the GPU underutilized (less than 20% utilization). Increasing the batch size to 64 pushed utilization above 80%, but latency jumped to over 200ms, unacceptable for the use case. 

A compromise that worked was dynamic batching using Triton Inference Server. It allowed me to set a maximum batch size and a timeout (e.g., 32 requests or 10ms), balancing latency and throughput dynamically. The gotcha is that tuning those timeouts isn't straightforward, it depends heavily on your traffic patterns. Without monitoring actual request distributions, it's easy to misconfigure and hurt both performance and responsiveness.
